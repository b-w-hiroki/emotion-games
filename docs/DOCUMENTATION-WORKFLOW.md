# 仕様書・設計書の更新ワークフロー

004「きえないで。」の現行仕様は [KIENAIDE-SPEC.md](./KIENAIDE-SPEC.md)、実装設計は [KIENAIDE-DESIGN.md](./KIENAIDE-DESIGN.md) を正本とする。過去の企画、台帳、監査、PRは判断の経緯であり、現行動作が食い違えばmainのコードとテストを確認して正本を修正する。仕様書と設計書には「これから作る案」を現行機能として書かない。

## 更新の単位

1. 機能・操作・文言・結末・数値・アクセシビリティが変わるPRでは、仕様書の該当節と受入基準を同じPRで更新する。
2. モジュール責務・状態・保存キー・素材パイプライン・音・QA経路が変わるPRでは、設計書の該当節を同じPRで更新する。両方に影響する場合は両方更新する。
3. 実装を変えない修正でも、文書の誤りを発見したら根拠となるコード・テストを照合して文書のみのPRを作る。
4. 実行時の挙動を変えない純粋なリファクタリング、テストだけの追加、CIメンテナンス等で正本を更新しない場合は、PR本文に `Docs impact: none — 理由` と明記する。単なる「不要」ではなく、何が変わらないかを具体的に書く。
5. PR本文の「文書への影響」「検証」「未検証」を埋める。レビューではコード・文書・テストを並べ、条件や数値の不一致、古い未完了表現、5文字程度の短い語尾だけの改行がないか確認する。

## 検証と公開

- `npm run verify` は文書の必須節・参照先を検査する。PRのCIでは、004に関わるコード／素材変更に対して仕様書または設計書の更新、あるいは理由付きの「影響なし」宣言を求める。これは更新漏れの検知であり、文書内容の正しさを自動保証しない。
- 実装変更の検証は既存のブラウザQA・キャプチャ・結末QAを省略しない。文書だけのPRにはコード変更のないことと参照先・説明の正確さを確認する。
- PRのチェック成功後にマージし、公開版で変更した操作を確認する。公開後に判明した差異は同じ文書を直す。実機／人の評価がない項目は「未検証」と残す。
- 「最終更新日」は更新した内容を実装と照合した日を記す。単なる定期日付更新や、監査ログへの追記だけで正本の更新を代替しない。

## 適用範囲

当面の機械的ゲートは004の実装、素材、QAスクリプトに適用する。他の19作品に同じ詳細文書を強制しない。新たに縦切り対象を決める時は [制作プレイブック](../studio-playbook/README.md) の依頼書から作品固有の仕様・設計の正本を作り、同じPR更新ルールへ追加する。
